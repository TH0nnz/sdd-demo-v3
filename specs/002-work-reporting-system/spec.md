# Feature Specification: 報工系統

**Feature Branch**: `002-work-reporting-system`  
**Created**: 2026-02-23  
**Status**: Draft  
**Input**: User description: "這是一套報工系統，共五種角色：管理層、PM、部門主管、執行人員、HR。管理層可建立修改刪除關閉專案並分派時數；PM拆分並指派 task、監控進度、不足時向管理層申請時數；部門主管查看部門工時與 task；執行人員填報工時消耗 task 時數不足通知 PM 只能編輯過去三工作天資料；HR 新增人員指派角色。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 執行人員填報每日工時 (Priority: P1)

執行人員登入後，可以看到所有指派給自己的 task 清單，選擇今日工作的 task 並輸入實際投入的工時（以 0.5 小時為最小單位）。填報提交後立即生效，系統自動扣減該 task 的剩餘時數，無需任何人員審核。若填報後剩餘時數歸零，系統提示執行人員通知 PM 申請增補時數。執行人員只能新增或修改過去三個工作天（週一至週五；不含假日）以內的填報紀錄，更早的紀錄為唯讀。若工作已完成但 task 時數仍有剩餘，執行人員可手動將 task 狀態設為「完成」。

**Why this priority**: 工時填報是整個系統的核心資料輸入點；若此流程無法正常運作，後續的進度監控、時數管理與報表功能均無意義。

**Independent Test**: 可單獨驗證——以執行人員帳號登入，對一個已指派的 task 填報工時，確認剩餘時數正確扣減，且超過三工作天的舊紀錄無法被修改。

**Acceptance Scenarios**:

1. **Given** 執行人員已登入且有一個狀態為「進行中」的指派 task，**When** 填報今日在該 task 投入 2 小時，**Then** task 的已消耗時數增加 2 小時、剩餘時數減少 2 小時，填報紀錄顯示在工時記錄列表中。
2. **Given** 執行人員嘗試修改 4 個工作天前的填報紀錄，**When** 點擊該筆紀錄，**Then** 系統顯示「超過可編輯期限（三工作天）」訊息，該筆紀錄仍為唯讀狀態。
3. **Given** task 剩餘時數在填報後歸零，**When** 填報完成，**Then** 系統顯示警示訊息提醒執行人員通知 PM 申請增補，並自動觸發一則站內通知給對應的 PM。
4. **Given** 執行人員判斷工作已完成但 task 仍有剩餘時數，**When** 將 task 狀態設為「完成」，**Then** task 狀態更新為「完成」，剩餘時數鎖定不再消耗，PM 在監控頁面可見到此狀態更新，且該 task 的工時填報功能立即凍結——執行人員嘗試對此 task 新增工時時系統顯示「task 已結束，無法新增工時」。

### User Story 2 - PM 管理 Task 並即時監控進度 (Priority: P2)

PM 可以在被指派的專案下，建立、修改、關閉、刪除 task，並將每個 task 配置一定的時數預算後指派給一名執行人員。PM 可在專案儀表板上即時（最多延遲 5 分鐘）查看每個 task 的狀態（待開始／進行中／完成／關閉）、已消耗時數與剩餘時數，以及整體專案的時數使用率。當任一 task 時數不足時，PM 可向管理層提交時數增補申請。

**Why this priority**: PM 是連接管理層與執行人員的樞紐；task 管理與進度監控是 PM 的核心業務，直接影響專案能否準時交付。

**Independent Test**: 可單獨驗證——以 PM 帳號建立一個 task 並指派給執行人員，確認執行人員填報工時後儀表板數字在 5 分鐘內更新。

**Acceptance Scenarios**:

1. **Given** PM 已被指派到一個專案，**When** 建立一個新 task 並設定 20 小時時數後指派給某位執行人員，**Then** 執行人員的 task 清單立即出現此 task，且專案剩餘時數對應減少 20 小時。
2. **Given** 執行人員剛填報了一筆工時，**When** PM 查看專案儀表板，**Then** 在 5 分鐘內可看到該 task 的已消耗時數與剩餘時數已更新。
3. **Given** 某個 task 剩餘時數為 0，**When** PM 提交增補時數申請（指定申請小時數與說明），**Then** 申請進入「待審核」狀態，管理層收到一則通知，申請清單在 PM 頁面可追蹤。
4. **Given** PM 關閉一個 task，**When** 操作確認，**Then** task 狀態更新為「關閉」，執行人員無法再對此 task 新增工時填報。

---

### User Story 3 - 管理層管理專案與審核時數申請 (Priority: P3)

管理層可以建立新專案，並設定專案名稱、總時數預算，以及指派負責的 PM。管理層可修改專案資訊、關閉專案或刪除尚未有工時紀錄的專案。當 PM 提交時數增補申請時，管理層可審核並核准或拒絕，核准後對應專案的可用時數立即增加。

**Why this priority**: 專案與時數的源頭控管由管理層負責；沒有正確的專案與時數分配，PM 和執行人員的工作流程均無法啟動。

**Independent Test**: 可單獨驗證——以管理層帳號建立一個專案並指派給 PM，確認 PM 帳號的可管理專案清單中出現此專案。

**Acceptance Scenarios**:

1. **Given** 管理層已登入，**When** 建立一個名為「產品改版」的專案，設定時數預算 200 小時並指派給特定 PM，**Then** 該 PM 的專案清單出現「產品改版」，可用時數顯示為 200 小時。
2. **Given** 一個專案已有工時紀錄，**When** 管理層嘗試刪除此專案，**Then** 系統拒絕刪除並提示「專案已有工時紀錄，請改為關閉」。
3. **Given** PM 提交了一筆 40 小時的增補申請並選擇「補至 task」，**When** 管理層確認目標層級並核准，**Then** 該 task 的可用時數增加 40 小時（專案總預算同步增加），PM 收到核准通知，申請狀態更新為「已核准」；若 PM 選擇「補至專案」，則 40 小時計入專案可用池，不直接分配給任何 task。
4. **Given** 管理層拒絕增補申請時填入拒絕原因，**When** 提交拒絕，**Then** PM 收到拒絕通知並可看到拒絕原因，申請狀態更新為「已拒絕」。

---

### User Story 4 - HR 管理使用者與角色 (Priority: P4)

HR 可以新增使用者帳號，填入姓名、所屬部門，並指派一個或多個角色（管理層、PM、部門主管、執行人員、HR）。HR 也可以變更現有使用者的角色或停用帳號。

**Why this priority**: 使用者與角色管理是整個系統的基礎設定；所有其他流程都依賴正確的角色指派。

**Independent Test**: 可單獨驗證——以 HR 帳號新增一個執行人員，確認新帳號可登入並看到執行人員專屬的操作介面。

**Acceptance Scenarios**:

1. **Given** HR 已登入，**When** 新增一名使用者（姓名、部門、角色：執行人員），**Then** 新使用者帳號建立完成，以此帳號登入後顯示執行人員操作介面。
2. **Given** 一名使用者目前角色為執行人員，**When** HR 新增「PM」角色給該使用者，**Then** 該使用者下次登入後可同時存取執行人員與 PM 的功能。
3. **Given** HR 停用一名使用者帳號，**When** 該使用者嘗試登入，**Then** 系統拒絕登入並顯示「帳號已停用，請聯絡 HR」。

---

### User Story 5 - 部門主管查看部門工時與 Task 狀態 (Priority: P5)

部門主管可以查看自己部門內所有執行人員的當前工時統計（本週、本月已填報小時數），以及各執行人員手上的 task 清單與狀態。部門主管的權限為只讀，不能修改任何資料。

**Why this priority**: 部門主管的監控功能不阻塞主要工作流程，且可於執行人員與 PM 流程穩定後再補充。

**Independent Test**: 可單獨驗證——以部門主管帳號登入，確認可看到部門內所有成員的工時與 task 資訊，且介面上無任何可修改資料的操作入口。

**Acceptance Scenarios**:

1. **Given** 部門主管已登入，**When** 查看部門工時總覽，**Then** 可看到部門內每位執行人員本週與本月的已填報工時合計。
2. **Given** 部門主管點擊某位執行人員，**When** 查看其詳情，**Then** 顯示該人員所有進行中與已完成 task 的清單，包含 task 名稱、所屬專案、狀態與已消耗時數。
3. **Given** 部門主管的操作介面，**When** 嘗試找到修改工時或 task 的入口，**Then** 介面上不存在任何編輯、刪除或修改功能。

---

### Edge Cases

- 執行人員在週一填報時，「過去三工作天」的計算範圍需正確包含上週五、週四、週三（跨週）
- Task 時數歸零後，執行人員仍嘗試填報工時：系統拒絕填報並顯示「task 時數已用盡，請等待 PM 增補」
- Task 標記為「完成」後，執行人員嘗試補填同日或回溯工時：系統拒絕並顯示「task 已結束，無法新增工時」，即使仍在三工作天可編輯期限內
- PM 申請增補的時數超過管理層設定的專案總預算上限：系統提示但仍允許申請，由管理層審核決定
- 同一使用者同一天對同一 task 重複填報：允許多筆，累計計算；當日總填報工時不得超過 24 小時
- 專案被管理層關閉後，PM 嘗試建立新 task：系統拒絕並提示「專案已關閉」
- 管理層嘗試關閉仍有非終態 task 的專案：系統阻止關閉並提示「請先關閉所有進行中的 task 後再關閉專案」
- 執行人員離職或被移出專案時，其所有非終態 task 轉為「未指派」並凍結工時填報；PM 重新指派後才可恢復填報
- 部門主管查看的部門範圍：僅能看到與自己所屬部門相同的執行人員資料，不能跨部門查看

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 管理層必須能夠建立、修改、關閉專案，並設定每個專案的總時數預算
- **FR-002**: 管理層必須能夠為每個專案指派負責的 PM（一個專案對應一個 PM）
- **FR-003**: 已有工時紀錄的專案，管理層只能關閉，不能刪除；無工時紀錄的專案可刪除
- **FR-004**: 管理層必須能夠審核 PM 提交的時數增補申請，並填入核准或拒絕的原因
- **FR-005**: PM 必須能夠在負責的專案下建立、修改、關閉、刪除 task，並設定每個 task 的時數配額
- **FR-006**: PM 必須能夠將 task 指派給單一執行人員
- **FR-007**: PM 必須能夠即時（最多 5 分鐘延遲）查看專案儀表板，顯示每個 task 的狀態、已消耗時數與剩餘時數
- **FR-008**: 當 task 剩餘時數歸零時，系統必須自動通知對應 PM
- **FR-009**: PM 必須能夠向管理層提交時數增補申請，並在申請時選擇補充目標層級（補至指定 task 或補回專案總預算池）；管理層核准時確認目標層級，核准後時數立即計入所選層級；PM 可追蹤申請狀態
- **FR-010**: 部門主管必須能夠以只讀方式查看所屬部門執行人員的工時紀錄與 task 清單
- **FR-011**: 執行人員必須能夠查看所有指派給自己的 task，並選擇 task 填報當日工時（最小單位 0.5 小時）
- **FR-012**: 執行人員填報的工時必須即時扣減對應 task 的剩餘時數；若 task 狀態為「完成」或「關閉」，系統必須拒絕填報並提示「task 已結束，無法新增工時」
- **FR-013**: 系統必須禁止執行人員新增或修改距今超過三個工作天（週一～週五，不含公假）的工時紀錄
- **FR-014**: 工作已完成時，執行人員必須能夠手動將 task 狀態設為「完成」，即使仍有剩餘時數；task 標記「完成」後，該 task 的工時填報功能立即凍結，不接受任何新增或修改
- **FR-015**: HR 必須能夠新增使用者（必填欄位：姓名、公司 email、所屬部門、至少一個角色），以及修改現有使用者的角色或停用帳號
- **FR-016**: 系統必須依據角色執行存取控制，確保每位使用者只能存取其角色所允許的功能與資料
- **FR-017**: 一位使用者可同時擁有多個角色，系統合併授予所有角色的權限
- **FR-018**: 系統必須採帳號密碼驗證，登入識別碼為使用者的公司電子郵件地址（全系統唯一）；所有新帳號的初始密碼統一為「Welcome123」，使用者首次登入後系統強制要求修改密碼方可繼續操作
- **FR-019**: 5 分鐘內連續登入失敗 15 次後系統必須鎖定帳號，並於 15 分鐘後自動解鎖
- **FR-020**: Task 狀態「完成」與「關閉」均為不可逆的終態；任何角色均不得將 task 從終態回退至其他狀態
- **FR-021**: 工時填報紀錄（WorkEntry）必須永久保留，不得透過任何事件（包含帳號停用、專案關閉、task 終態）導致刪除
- **FR-022**: 工時填報提交後必須立即生效，時數即時從對應 task 扣減；系統不支援「待審核」中間狀態，無需任何角色審核確認
- **FR-023**: 密碼複雜度規則：至少 8 個字元，必須同時包含大寫字母、小寫字母與數字；不符合規則時系統拒絕設定並提示具體要求
- **FR-024**: 系統必須對下列關鍵操作自動留存稽核日誌（AuditLog），每筆記錄包含操作人員、操作時間與內容摘要，且不得刪除：使用者角色變更、帳號啟停、時數增補申請審核決定、PM 強制關閉 task
- **FR-025**: 管理層關閉專案時，系統必須檢查該專案下是否仍有非終態（待開始／進行中）的 task；若有，系統必須阻止關閉並提示「請先關閉所有進行中的 task 後再關閉專案」
- **FR-026**: 當執行人員離職（帳號停用）或被移出專案時，系統必須將該人名下所有非終態 task 轉為「未指派」且凍結工時填報；PM 重新指派後，task 恢復可填報狀態

### Key Entities

- **Project（專案）**: 代表一個業務項目，具有名稱、狀態（進行中／關閉／刪除）、總時數預算、已消耗時數、負責 PM、建立時間與關閉時間
- **Task（工作項目）**: 屬於某個專案的工作單元，具有名稱、狀態（待開始／進行中／完成／關閉）、配額時數、已消耗時數、指派的執行人員（可為「未指派」）；「完成」與「關閉」為不可逆終態，任何角色均不得回退
- **WorkEntry（工時填報）**: 執行人員對特定 task 在特定工作日填報的工時紀錄，包含填報人員、task、日期、填報小時數、建立與最後修改時間；永久保留，不得刪除
- **User（使用者）**: 系統帳號，具有姓名、公司電子郵件地址（唯一，作為登入識別碼）、所屬部門、一個或多個角色、帳號狀態（啟用／停用）
- **Department（部門）**: 組織單位，具有部門名稱，關聯部門主管與所屬執行人員
- **HoursRequest（時數申請）**: PM 向管理層提交的增補申請，包含所屬專案、申請人、申請時數、說明、補充目標層級（task 或專案）、目標 task（選填，僅補至 task 時填入）、狀態（待審核／已核准／已拒絕）、審核人與審核意見
- **AuditLog（稽核日誌）**: 系統自動產生的關鍵操作記錄，包含操作類型、操作人員、操作時間、受影響的實體識別碼與內容摘要；永久保留，不得刪除

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 執行人員完成一次工時填報操作（選擇 task → 輸入時數 → 確認）所需時間不超過 2 分鐘
- **SC-002**: PM 在專案儀表板看到的 task 進度資料，延遲不超過 5 分鐘（相對於實際填報時間）
- **SC-003**: 系統對「過去三工作天以外的工時紀錄不可編輯」規則的執行率為 100%，無任何繞過途徑
- **SC-004**: 時數不足通知（task 歸零時 → 通知 PM）在填報動作完成後 1 分鐘內送達
- **SC-005**: 95% 的使用者在首次嘗試時即可成功完成其主要日常操作（工時填報或 task 審核）
- **SC-006**: 系統在任意時間點均能正確呈現各專案與 task 的已配額、已消耗、剩餘時數，誤差為零
- **SC-007**: 角色存取控制確保每位使用者無法存取其角色未授權的任何功能或資料，歷次測試通過率 100%
- **SC-008**: 系統在 100 名使用者同時操作時，一般頁面回應時間 p95 不超過 500 ms，歷史查詢不超過 3 秒

## Scalability & Non-Functional Constraints

- **使用者規模**: 小於 100 名同時線上使用者；系統設計不需支援水平擴展，單一部署在內部網路即可
- **可用性**: 工作日 08:00–20:00 為核心使用時段；系統自然異常後應能在 15 分鐘內恢復服務
- **回應時間**: 图形介面操作的一般請求 p95 回應時間不超過 500 ms；历史資料查詢可容許最長 3 秒

## Security & Privacy

- 使用者驗證：帳號密碼登入；初始密碼統一為「Welcome123」，首次登入強制修改
- 密碼儲存：密碼必須以不可逆雜湊（加鹽）方式儲存；明文密碼不得出現在任何日誌或回應中
- 密碼複雜度：至少 8 個字元，必須包含大寫字母、小寫字母與數字；不符合規則的密碼系統拒絕設定
- 5 分鐘內連續登入失敗 15 次後鎖定帳號，15 分鐘後自動解鎖
- 所有 API 請求必須攜帶驗證 token；未驗證的請求回傳 401，無權限的請求回傳 403
- 角色存取控制（RBAC）確保資料隔離：執行人員只能見到指派給自己的 task；部門主管只能見到本部門資料；PM 只能存取自己負責的專案
- 稽核日誌：下列關鍵敏感操作必須留存不可刪除的稽核記錄，每筆包含操作人員、操作時間與內容摘要：
  - 使用者角色的新增、變更與移除
  - 帳號啟用與停用
  - 時數增補申請的核准或拒絕決定（含審核人與意見）
  - Task 被 PM 強制關閉（非執行人員主動完成）

## Assumptions

- 「工作天」定義為週一至週五；本版本不處理國定假日的排除邏輯
- 工時填報的最小單位為 0.5 小時，每日同一 task 可多次填報，累計不超過 24 小時
- 一個專案只由一名 PM 負責（不支援共同 PM）
- 一個 task 只能指派給一名執行人員（不支援共同執行）
- 部門主管只能查看與自己相同部門標記的執行人員，不支援跨部門查看
- 使用者帳號由 HR 管理；本版本不包含使用者自助註冊功能
- 每位使用者的公司電子郵件地址在系統中必須唯一，不得重複指派，初始密碼都是「Welcome123」，首次登入後強制修改
- 通知機制採站內訊息（in-app notification）；本版本不包含電子郵件或簡訊通知
- 工時填報紀錄永久保留，不得透過任何事件導致刪除
